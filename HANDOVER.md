# VDR Digital Term Sheet — handover to Lovable

Single-tranche vanilla Eurobond, draft 3. This folder contains everything needed to rebuild the
term sheet in the VDR without losing anything that makes it correct.

## What is in here

| Path | What it is | Rebuild from scratch? |
|---|---|---|
| `src/fields.js` | The 197-field dictionary, stages, enumerations, sections | **No. Copy verbatim.** |
| `src/order.js` | Child element order per parent, generated from the XSD | **No. Regenerate from the XSD only.** |
| `src/bdt-xml.js` | BDT 2.0 XML serialisation | No. Copy verbatim. |
| `src/validate.js` | Compliance and consistency checks, LEI and ISIN validators | No. Copy verbatim. |
| `src/legends.js` | Standard legends generated from field values | No. Copy, then have counsel review wording. |
| `src/envelope.js` | VDR routing envelope: stage, lineage, execution fields | No. Copy verbatim. |
| `src/termsheet.js` | Human-readable rows, plain text, chat block | No. Copy verbatim. |
| `src/ingest.js` | Assisted fill from BDT XML and prose documents | No. Copy verbatim. |
| `src/model.js` | State shape and auto-maintained fields | No. Copy verbatim. |
| `src/example.js` | Worked example, fictional entities | No. Useful as a fixture. |
| `reference/…html` | The working reference implementation, one self-contained file | Reference only. **Rebuild the UI.** |
| `schema/*.xsd` | ICMA BDT 2.0 schema, for validation in CI | No. |
| `verify.mjs` | Proof the modules behave identically | Keep as a test. |

The split matters. **The UI is the part worth rebuilding in React; the core is the part worth
preserving exactly.** Every module in `src/` is pure: it takes a `state` object and returns a
value. None of them touch the DOM, so they drop into a React, Vue or server-side project unchanged.

## Invariants — do not let a rebuild break these

1. **Element order comes from the XSD, not from code order.** `ORDER` in `src/order.js` was
   generated by walking `icma-bond-data-taxonomy.xsd`. Serialisation sorts siblings by those lists.
   This is why fields can be added to the dictionary anywhere without breaking validity, and why
   hand-maintaining the order would be a mistake. Moving to BDT 2.1 means regenerating this file,
   not editing it.
2. **The output must validate.** `xmllint --schema schema/icma-bond-data-taxonomy.xsd module-output.xml --noout`
   should pass, for a fully priced deal and for a sparse announcement-stage record. Wire this into CI.
3. **`GoverningLaw` is an `xs:choice`.** Country code, subdivision code or free text — never more
   than one. The jurisdiction-of-courts clause therefore lives in the envelope, not the payload.
   A rebuild that "helpfully" adds both will produce invalid XML.
4. **Execution fields never enter the BDT payload.** Fields marked `ext: 1` (IPTs, guidance, spread
   set, book size, timing, fee split, stabilisation period) have no BDT home. They travel in the
   envelope and are mirrored as text into `AdditionalIssuanceInformation`. Do not invent BDT
   elements for them.
5. **Stage drives requirement, not visibility alone.** `req` is the stage from which a field is
   mandatory; `from` is the stage from which it is relevant. 42 fields are required at announcement,
   82 by pricing. Release is blocked while any `fail` check stands.
6. **Assisted fill never writes a field.** `ingestBDT` and `ingestText` return proposals. A person
   accepts or ignores each one. This is the human-in-the-loop requirement and is not optional.
7. **Each release is a full snapshot** with a `supersedes` pointer, not a delta. A consumer that
   missed a message is never left with a partial picture.
8. **Document status is not execution stage.** BDT offers PENDING, ISSUED and WITHDRAWN only.
   The seven-stage execution model lives in the envelope.

## What to build fresh in Lovable

The interface, and only the interface:

- Form rendering driven by `SECTIONS` and `FIELDS`, collapsed by default to what the stage requires,
  with a per-section expander and a global "show every field" toggle.
- Repeating groups for parties (with multi-role selection and nested ratings), identifiers, ratings,
  documents and contacts.
- Tabs: Fill, Term sheet, Legends, BDT XML, Envelope, Distribution, Release log.
- The stage rail, the live checks panel, the release flow with authorisation and version increment.
- Document drop with the review panel for proposals.

## Things that must change in a real deployment

- **Persistence.** The reference implementation keeps drafts in `localStorage`. The VDR needs
  server-side state against the deal record, with per-user edit attribution.
- **Downloads.** The reference uses an environment-specific API. Use a Blob and object URL.
- **PDF and Word parsing** loads pdf.js and JSZip from a CDN at runtime. Pin them as npm
  dependencies instead.
- **Extraction quality.** Client-side pattern rules are deliberately conservative and will miss
  values. Server-side extraction with a model behind it would raise the hit rate substantially,
  feeding the same review panel. Keep the review panel either way.
- **Entitlements.** Subscriber routing, acknowledgement tracking and per-deal entitlement checks are
  out of scope in the reference and are the main missing piece before release is real.

## Prompt to give Lovable

> I am adding a digital bond term sheet to this project. The `src/` folder contains the finished,
> tested core logic as framework-agnostic ES modules: an ICMA Bond Data Taxonomy 2.0 field
> dictionary, XML serialisation, validation rules, legend generation and document extraction.
>
> Do not rewrite, regenerate or "improve" anything in `src/`. Import it. In particular do not
> reorder or edit `src/order.js` or the field paths in `src/fields.js`: they are derived from the
> ICMA XSD and the XML output is schema-validated against it.
>
> Build a React interface over that core:
> - A form driven by `SECTIONS` and `FIELDS` from `src/fields.js`. Each field renders by its `t`
>   (text, num, date, sel with options from `E[fd.e]`, bool, ta, group).
> - Sections collapsed by default: show only fields where `req <= state.stage`, or that already hold
>   a value, or that have a pending proposal. Everything else behind a "Show N optional fields"
>   expander, plus a global toggle.
> - A seven-stage rail from `STAGES`; changing stage changes which fields are mandatory.
> - Repeating groups from `GROUPS`: parties (multi-select roles, nested ratings), identifiers,
>   ratings, documents, contacts.
> - Tabs: Fill, Term sheet (`sheetRows`), Legends (`legendBlocks`), BDT XML (`buildXML`), Envelope
>   (`buildEnvelope`), Distribution, Release log.
> - A live checks panel from `checks(state)`; block release while any `l === "fail"` remains.
> - Release: capture the authorising bookrunner, increment the version, append to the release log
>   with a full snapshot, and show a field-level diff against the previous release.
> - Document drop calling `ingestBDT` / `ingestText`, rendering the returned proposals in a review
>   list with Accept and Ignore per row. Never apply a proposal automatically.
>
> Persist state server-side against the deal, not in localStorage. Use a Blob for file downloads.
> Keep `verify.mjs` passing.

Use `reference/vdr-digital-term-sheet-reference.html` as the visual and behavioural reference:
open it in a browser to see exactly what the finished thing does.
